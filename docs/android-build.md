# Android build (Capacitor)

The Android app is this same React web app wrapped by [Capacitor](https://capacitorjs.com)
into a real installable app — no code was rewritten. The `android/` folder is a
genuine Android Studio project generated by `npx cap add android`.

## One-time setup on your machine

1. Install **Android Studio** (includes the Android SDK).
2. `pnpm install`

## Building the web bundle into the Android app

Capacitor doesn't rebuild your web app for you — run this after any change
you want to see on Android:

```bash
pnpm android:sync   # vite build, then copies dist/ into android/app/src/main/assets/public
pnpm android:open   # opens the android/ folder in Android Studio
```

In Android Studio: press Run to install on a connected device/emulator, or
**Build → Generate Signed App Bundle** when you're ready for Play Store.

## Pointing the app at a real backend

In local web dev, API calls use relative paths (`/api/...`) because Vite's
dev server proxies them to `server/index.mjs` on the same origin. A packaged
Android app has no such proxy — it needs the **absolute URL of your deployed
backend**.

Before running `pnpm android:sync` for a real device/Play Store build, create
`.env.production` (not committed) with:

```
VITE_API_BASE_URL=https://your-deployed-backend.example.com
```

Vite picks this up automatically for production builds. Without it, API
calls from the installed app will fail (they'd try to hit the app's own
`capacitor://localhost` origin).

## Backend

`server/index.mjs` now talks to **Postgres** (via `DATABASE_URL`), not
SQLite. It needs to run somewhere reachable from the internet before the
Android app can log in or submit restaurants/mosques — this repo doesn't
include a hosting setup yet. Options: Render, Railway, Fly.io, or any VPS,
paired with a hosted Postgres (Neon, Supabase, Railway Postgres, RDS, etc).

Once deployed, run the schema once (the server creates its own tables on
boot — just start it once with `DATABASE_URL` pointing at the production
database) and set `VITE_API_BASE_URL` to that server's URL as above.

## What's already wired for crowdsourced data

- `POST /api/restaurants`, `POST /api/mosques` — authenticated users submit
  a restaurant or mosque/prayer-room; every submission starts as `pending`.
- `GET /api/restaurants?status=approved`, `GET /api/mosques?status=approved`
  — what the public map should read from once wired up.
- `GET /api/admin/submissions?status=pending` +
  `POST /api/admin/restaurants/:id/approve|reject` (and the mosque
  equivalent) — moderation, admin-role only.
- In the app: Home screen has "+ Restoran qo'shish" / "+ Masjid qo'shish"
  buttons wired to real submission forms (`src/screens/ContributeScreens.tsx`)
  that call the API above and show a real pending/approved state.

Not yet done (next steps): wiring the admin dashboard's existing UI to these
moderation endpoints (it currently shows mock data), and swapping the
restaurant/mosque *display* screens (Home, RestaurantList, MosqueList) from
their hardcoded sample arrays over to `GET /api/restaurants` /
`GET /api/mosques` once there's enough approved real data to show.
